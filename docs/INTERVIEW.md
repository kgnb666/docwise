# 面试题库：DocWise 项目 20 问（含参考答案）

> 所有答案都对应项目里的真实实现。面试前把每个问题自己讲一遍，讲不顺的就回去看代码。
> 原则：**不知道就说"这里我当时的做法是…，如果重新做我会…"**，比硬编强一百倍。

## 一、架构与设计（5 问）

**Q1. 介绍一下你的项目整体架构？**
> 30 秒版：React 前端通过 SSE 调 FastAPI 后端。后端链路是：文档上传 → 解析（txt/md/pdf）→ 标题感知分块 → 向量化 → 入向量库；问答时：追问改写 → 混合检索（BM25+向量）→ Rerank 精排 → 组装 Prompt → 流式生成，回答带引用出处。启用了 Agent 时走 Function Calling 工具闭环。旁边还有评测体系：离线命中率对比 + LLM-as-Judge 生成质量打分。

**Q2. 为什么选 FastAPI 而不是 Flask/Django？**
> 原生 async/await，SSE 流式输出天然适合；Pydantic 做请求校验；自动生成 OpenAPI 文档。Flask 的流式要自己折腾 WSGI，Django 偏重，对这个场景 FastAPI 是性价比最高的。

**Q3. 为什么前端要 SSE 而不是 WebSocket？**
> 这是单方向的"服务器推文本"，不需要双向通信；SSE 基于 HTTP，走普通负载均衡没问题、断线自动重连、实现简单。WebSocket 是双向的，适合聊天室那种交互，这里用不上。真需要双向再换。

**Q4. 向量库为什么先用内存实现？**
> 接口先行：`VectorStore` 定义了 add/search/delete/count/revision，内存实现先验证检索逻辑。数据量上来后换 FAISS（ANN 索引）或 pgvector/Milvus（持久化、多租户、横向扩展），业务代码零改动——这是为了把"存储选型"和"业务逻辑"解耦。

**Q5. 为什么做一个评测体系？**
> RAG 系统最怕"感觉效果不错但说不出好在哪"。我用自建测试集（问题+期望来源文档）跑四档对比（纯向量/混合/混合+OverlapRerank/混合+bge-reranker API）得到命中率；再用 LLM-as-Judge 打忠实度和相关性分。没有评测，优化就是玄学；有评测，每次改动都能用数字验证。

## 二、检索细节（6 问）

**Q6. 为什么要混合检索？纯向量检索哪里不行？**
> 向量检索擅长"意思相近但用词不同"，但精确匹配（型号、代码、人名）容易漏；BM25 反过来，精确词强、同义改写弱。我把两者 min-max 归一化后按 alpha 加权融合（默认 0.4 偏向量、0.6 偏关键词——alpha 越大越偏 BM25）。实测单靠任一种都有明显漏检场景。

**Q7. BM25 是自己实现的？讲讲公式？**
> 对，零依赖实现。score = Σ idf(t) × tf(t,d)×(k1+1) / (tf(t,d) + k1×(1−b+b×|d|/avgdl))，k1=1.5、b=0.75 是经典参数。idf 用平滑版 ln((N−df+0.5)/(df+0.5)+1)，避免除以零。中文分词先用"单字+相邻二元组"的轻量方案，后面可以换 jieba。

**Q8. 分块大小怎么定的？为什么 800/重叠 100？**
> 800 字符大致是中文 10-15 句话，语义完整且不会超过上下文预算；重叠 100 保证切缝处不丢关键信息（比如一句话刚好跨块）。其实没有最优解，我做了个"分块大小对命中率的影响"实验对比过，最后取的这个值。面试加分点：**分块参数应该用评测数据定，不是拍脑袋**。

**Q9. Rerank 是干嘛的？你的实现是什么级别？**
> 粗召回用的都是轻量打分，只保证"相关的大概率在前"。Rerank 对 top-k 候选用更强的打分重排。我实现的是轻量重叠精排（query 与候选的 token Jaccard 重叠度加权），作为 MVP 占位；接口留好了，下一步换成 bge-reranker 交叉编码模型——那个才是工业级做法。诚实说明层级很重要。

**Q10. 追问怎么处理？**
> 检测指代词（它/这个/上面/刚才…），命中就用最近一轮用户问题做上文，拼接成自包含查询再检索（如"它有哪些优点"→"什么是RAG 它有哪些优点"）。这是启发式版本，可以换 LLM 改写，更准但多一次调用。

**Q11. 检索结果缓存是什么思路？**
> key 是改写后的查询文本，value 是检索结果（chunk 列表），TTL 300 秒。命中缓存就跳过 embedding 调用——embedding 是每次问答里最贵的一步。接口留了 Redis 的位，多实例部署时换成集中式缓存。

## 三、Agent（3 问）

**Q12. Agent 的工具调用循环怎么实现的？**
> 把 messages + 工具 schema 发给 LLM，流式聚合分片 tool_call（同一 index 是一次调用的多个分片），执行 handler（支持同步/异步），按 OpenAI 协议回填 role=tool 消息，再继续下一轮，直到模型不再调用工具。过程中 delta 全程透传给前端，另发 tool_result 事件展示"Agent 做了什么"。

**Q13. 怎么防止死循环/费用失控？**
> 三层防护：① `agent_max_turns` 硬上限（默认 5），到顶强制结束；② 工具结果截断回填（2000 字符），防止上下文爆炸；③ 接口层令牌桶限流（默认容量 20、每秒补 1 个），防止 Key 被刷。这三层是分开的：Agent 防逻辑失控，限流防外部攻击。

**Q14. 工具是怎么注册的？加一个新工具要几步？**
> 一个 Tool 对象四要素：name、description（给 LLM 看的）、parameters（JSON Schema）、handler。注册进 TOOL_REGISTRY 就完事，执行器自动把它挂给 LLM。目前内置计算器（参数白名单正则校验防注入）和维基百科搜索（免费 API 演示联网）。

## 四、评测（3 问）

**Q15. 你的命中率数据是怎么来的？**
> 自建 32 条测试集（问题 + 期望来源文档），语料是 10 篇技术笔记（40 块，故意包含主题重叠的文档）。对每个问题：向量化 → 检索 → 看期望文档在不在结果里，跑四档配置对比（纯向量 / 混合 / 混合+OverlapRerank / 混合+bge-reranker API），输出 JSON 报告到 docs/eval/。**实测（真实 embedding：bge-m3）：top-1 严格模式下纯向量 96.9% → 混合检索 100%**。这里有个方法论要点：top-k 越大指标越容易饱和（top-5 时四档全 100%），**要选能暴露差距的粒度去评测**。

**Q15.5. 有没有具体案例说明混合检索比纯向量好？**（追问概率高）
> 有。top-1 时纯向量漏掉一题：「Transformer 为什么是大模型的基石」。我语料里有两篇都提到 Transformer 和大模型的笔记，纯向量被"大模型笔记"的语义带偏了；混合检索靠 BM25 的精确关键词命中"深度学习的 Transformer 章节"，修正了结果。**这个案例量化了混合检索的价值——语义相近的跨主题问题上，关键词信号是重要的纠偏器。**

**Q16. 忠实度和相关性怎么打的分？**
> LLM-as-Judge：把（问题、回答、检索到的资料）发给 Judge 模型（DeepSeek，temperature=0），要求输出 JSON 分数。忠实度看回答是否严格基于资料；相关性看是否切题。解析做了三层容错：整体 JSON → 提取 JSON 片段 → "X/10" 启发式。**实测（32 题）：忠实度 / 相关性均 0.99**。

**Q16.5. 评测过程中遇到过什么问题吗？**（加餐题，讲这个很加分）
> 有三个。第一个：忠实度 0.25 → 定位为引用预览截断污染判分上下文 → 修复后 0.99。第二个：Transformer 跨主题漏检 → 混合检索 BM25 纠偏。第三个（做"知识库外问题兜底"时）：给检索加相关度阈值，第一版用归一化后的混合分做过滤——实测发现 min-max 归一化会把小语料最高分顶到 1.0，阈值形同虚设（"中秋节"对运维文档打出 0.70）；改成**原始向量余弦**做阈值后，用真实数据探测确定 0.4 正好分开无关(0.31)/相关(0.67)。**三个案例的共同点：评测/实测数据驱动，而不是拍脑袋。**

**Q17. 如果评测分数低，你会怎么排查？**
> 先分层：检索问题还是生成问题。命中率低 → 查分块、embedding、alpha、Rerank；命中率高但忠实度低 → 查 Prompt 是不是没约束住模型、**上下文是不是被截断**（我踩过这个坑）；相关性低 → 查改写和检索排序。每改一处重跑同一份测试集，看数字动没动。

**Q17.5. 用户问知识库外的问题（比如生活常识）怎么办？**（产品权衡题）
> 两种模式可配置：strict（只答知识库，"资料中没有"）和 chat（检索未命中时让模型用常识回答，可调维基百科工具）。判定"未命中"靠**相关度阈值**（原始余弦，实测 0.4 分开无关/相关）。这是个产品决策：知识库工具要防幻觉人设，通用助手要可用性——我做成开关，两种都支持。

## 五、工程化（3 问）

**Q18. 限流参数为什么是 20/秒补 1？**
> 容量 20 允许短突发（演示时连续问几句不卡），每秒补 1 是长期稳定速率，20 QPM 对个人项目足够且省 Key 钱。参数可配（.env），多实例部署时换 Redis 集中式。面试点：**限流参数要结合成本和用户体验权衡，不是越大越好**。

**Q19. 流式断线了怎么办？**
> 后端是生成式 SSE：断线时前端收到 error 事件提示重试；数据一致性上，回答是一次性生成的，重试会产生新回答，不是大问题。严谨方案是加 request id + 事件序号做幂等，这个在 TODO 里。

**Q20. 测试怎么组织的？**
> pytest，54 个用例，全部离线可跑（哈希嵌入 + 假 LLM），CI 里 pytest + 前端 build 两个 job。覆盖：分块边界、中文分词、BM25 排序、混合检索、向量库 CRUD、PDF 解析（mock）、端到端上传检索、Agent 循环（假 LLM 脚本化事件）、限流 429、评测执行器聚合。**"没有外部依赖也能全量测试"是我刻意做的设计**。

## 六、送命题

**Q21. 这个项目最大的难点是什么？**
> 不是写代码，是**让效果可验证**。RAG 链路长，任何一环出问题（分块切断了语义、embedding 没对准、Prompt 没约束住幻觉）都很难肉眼发现。所以我从第一天就搭评测：先证明"检索准"，再证明"生成好"，每一步都有数字。这也是我认为这个项目区别于课程作业的地方。

**Q22. 如果给你两周，你最想加什么？**
> ① 换 bge-reranker + 真实 embedding，把评测对比曲线做出来（简历上的硬数据）；② 用真实知识库内容扩充测试集到 50 条；③ 上线部署 + 录演示视频。技术方向其实都留好口了，主要缺真实数据和 Key。
